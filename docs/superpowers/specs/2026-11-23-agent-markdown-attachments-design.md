# Agent Markdown 与素材输入设计

**日期**：2026-11-23
**状态**：已批准（方案 2，2026-11-23）
**范围**：AI 项目会话的 Markdown 展示、图片/文本附件输入与多模态模型传输

## 意图

让 Autoforge Agent 会话能正确展示 AI 生成的 Markdown，并让用户可以把图片和常见文本资料作为问题上下文交给 Agent。目标是打通从选择素材、会话保存、模型请求到历史消息再打开的完整链路；单独增加上传按钮不能解决问题，因为目前 Provider 协议也只传字符串。

## 现状依据

- `AiProjectWorkspace.vue` 使用 `<pre>` 显示完整回复和流式回复，因此 Markdown 语法按普通字符串展示。
- `LlmMessage.content` 为字符串；OpenAI、Anthropic、Gemini 的消息转换都按纯文本序列化。
- AI 项目轮次表仅保存文本、文件变更、检查结果及导入脚本 ID，没有附件记录。
- 现有参数附件组件将本机路径保存为脚本运行参数，Agent 会话不能读取这些文件，也不能把图片作为模型视觉输入。
- 项目已有 `markdown-it` 和 `dompurify` 依赖，可用于安全 Markdown 渲染；暂不需要新增渲染依赖。

## 目标

- 历史与流式 Agent 回复都渲染常用 Markdown：标题、段落、强调、链接、引用、表格、列表、行内代码和代码块。
- 原始 HTML 默认不执行；输出经过净化。Markdown 链接限制为安全的 HTTP/HTTPS 目标；远程 Markdown 图片不自动加载。
- 对话输入支持常见栅格图片及 UTF-8 文本资料。首期文本资料包括 Markdown、纯文本、JSON、代码和日志；每个文件作为有文件名边界的上下文片段传给模型。
- 图片作为真正的多模态输入发送：OpenAI 与 OpenAI-compatible 使用 OpenAI 图像内容块，Anthropic 使用 image source 内容块，Gemini 使用 inlineData 内容块。
- 上传后显示待发送素材名；图片在待发送状态可预览。发送后素材与用户轮次关联，重开项目仍可看到素材名并由同一会话继续引用。
- 用户可在发送前移除素材；会话消息能区分正文和附件，流式回复不会破坏已发送消息的附件呈现。
- 附件只复制到 Autoforge 私有用户数据目录；Renderer 和模型 prompt 不接收任意本机路径。删除项目时清理由该项目拥有的附件。
- 对不支持的文件类型、非 UTF-8 文本、超限附件或拒绝图片输入的模型，显示清楚的错误；不得悄悄删掉附件或假装已传给模型。

## 非目标

- PDF、DOCX/Office、压缩包解析、OCR、网页抓取或自动解压。
- Markdown 的任意 HTML、脚本执行、远程图片预览或模型输出中的文件链接自动下载。
- 更改模型供应商配置、凭据体系、项目 Agent 工具权限或脚本执行能力。
- 把附件二进制打包进对话 JSON 导出。导出可标注附件文件名和媒体类型，但附件内容仍留在本机。

## Approaches

1. **仅在界面渲染 Markdown**：将消息字符串转换为安全 HTML。改动小，但图片和素材仍无法进入模型上下文，也不能满足本次反馈。
2. **会话级附件与 Provider 多模态链路（推荐）**：增加项目附件选择/私有暂存、轮次元数据持久化、文本内容上下文、三家 Provider 图片格式转换、附件预览及 Markdown 净化渲染。覆盖用户反馈，同时限制在图片与可读文本范围。
3. **通用素材摄取**：在方案 2 上加入 PDF/Office、OCR、压缩包和其他格式解析。覆盖更广，但需要更多解析依赖、恶意文件边界、内容截断/Token 预算和格式兼容验证；不作为本次首期范围。

**采用方案**：方案 2，用户已选择“常见输入优先”。复用现有 `markdown-it`、`dompurify`、Electron 文件选择与主进程存储模式；首期不引入 PDF/Office 或 OCR 解析器。

## 用户流程与界面

```text
Agent 回复：Markdown 标题、正文、列表、代码块按格式显示

┌───────────────────────────────────────────┐
│ [图片缩略图] [需求说明.md ×]               │
│ 描述你想创建或修改的脚本……                 │
│ [+ 添加图片或文本文件]              [发送] │
└───────────────────────────────────────────┘

发送后：用户气泡保留正文和附件名/图片预览；历史重载后附件仍可识别。
```

1. 用户在输入区通过“添加图片或文本文件”打开系统多选对话框。
2. 主进程验证项目存在、文件类型/大小/数量与实际内容，复制到项目私有附件目录，返回不含本机路径的 ID、文件名、媒体类型、大小和图片预览数据。
3. 用户在输入区看到附件列表，可移除后再发送；发送动作把附件 ID 与正文一起传给 Agent。
4. 主进程从受控附件存储读取素材。文本资料以分隔清楚的文件名和正文加入用户消息；图片保持独立附件元数据，由 Provider 适配器转换为对应视觉格式。
5. 用户消息正文与附件引用落入会话；流式 Agent 回复按 Markdown 安全渲染。重新打开会话时显示附件名称，图片可通过有大小上限的主进程读取接口预览。
6. 现有模型配置不声明视觉能力。用户发送图片时由 Provider 尝试请求；若模型拒绝，界面保留这轮消息和附件并提示换用支持图片的模型重试，不静默丢图。

## 数据与安全边界

- 在 SQLite 新增 AI 项目轮次附件元数据列，单条轮次保存附件 ID、显示名、媒体类型和长度等信息；二进制只保存在用户数据目录，不存入数据库。
- 附件 ID 由主进程生成，存储路径由主进程根据项目 ID 和附件 ID 解析。IPC 只接受项目 ID 与附件 ID，不接受任意目标路径。
- 文件选择通过 Electron 系统对话框执行。导入时检查常见图片魔数和允许的文本格式，拒绝 SVG、可执行文件、未知二进制及符号链接。
- 设置单文件/单图片、单轮附件数量、文本内容长度、图片总量及模型请求上下文上限；超过限制时返回明确可操作的信息。限制的精确值由实现者结合 Provider 限制和现有上下文上限决定，并写入常量及测试。
- 图片传输在主进程将字节读入受限内存缓冲后编码为 Provider 请求内容；不得向日志写入 Base64、图片数据或用户附件文本。
- 文本附件仅按严格 UTF-8 读取；不执行内容，不把附件文本解释为 Agent 工具指令。Agent 仍遵守原项目系统提示和项目路径工具约束。
- 删除项目记录时，在主进程清理其附件目录；单项删除只允许删除该项目拥有的附件 ID。
- Markdown 渲染关闭原生 HTML，先由 `markdown-it` 生成，再由 `DOMPurify` 按允许的标签、属性和 URL 协议净化；代码块不作为 HTML 执行。流式未闭合代码围栏按 Markdown 当前可解析结果显示。
- 未发送附件取消/移除时由主进程回收孤儿文件；需要覆盖应用关闭或崩溃后遗留暂存素材的清理策略。

## Provider 契约

- `LlmMessage` 增加类型化附件数据或受控二进制引用，文本 `content` 保持现有字符串语义，以兼容现有纯文本/工具调用路径。
- Agent 在提交普通用户轮次时把附件引用纳入轮次持久化；构建历史消息时按 ID 解析有效附件。附件已缺失时明确提示用户，普通历史文本仍可查看。
- OpenAI 与 OpenAI-compatible 将图片编码为 `image_url` 的 data URL；Anthropic 将图片编码为 Base64 source；Gemini 以 `inlineData` 编码。三类适配器保留同一轮中的文本顺序与图像顺序。
- 纯文本 Provider 请求与现有工具调用不改变行为。当前 `LlmProfile` 没有视觉能力标记，本次不扩展模型设置；若图片请求被 Provider 拒绝，Renderer 显示可理解错误并保留该轮及附件以便用户换模型重试。

## 验收标准

1. Markdown 历史消息和流式消息显示标题、段落、列表、链接、表格与代码块；恶意 HTML、`javascript:` URL 不执行，远程 Markdown 图片不加载。
2. 用户能选择并移除支持的图片/文本附件，发送后用户消息可区分正文与素材，应用重启后会话仍能列出附件。
3. 文本附件内容实际到达模型请求并包含清晰文件名边界；超长或无效 UTF-8 内容被明确拒绝/截断并告知用户。
4. 图片请求在 OpenAI、OpenAI-compatible、Anthropic、Gemini 的测试中生成正确的请求内容块；测试验证 Base64 对应真实样例字节且日志不泄漏原始内容。
5. 模型不支持视觉时，选择图片后的操作结果明确；不得无提示地静默丢弃图片。
6. IPC 不能借附件 ID 读取其他项目文件或任意本机路径；删除项目清理其附件，但不触碰其他项目附件。
7. 既有纯文本对话、工具轮次、取消、项目切换和运行时参数附件行为不回归。

## 留给实现者的决定

- Attachment/preview IPC 的拆分方式与每次读取的字节上限；Renderer 不取得绝对路径。
- 图片本地预览采用小尺寸缩略图数据还是按需 IPC 读取；优先避免将整幅原始 Base64 重复传输。
- 支持的图片扩展名与魔数集合；建议首期 PNG、JPEG、WebP、GIF，并显式拒绝 SVG。
- 支持的文本扩展名白名单和截断策略；附件内容需从始至终计入 `MAX_CONTEXT_CHARS`，并为图片预留 Provider 请求预算。
- 清理孤儿暂存附件的触发时机和年龄阈值；项目删除的附件清理必须确定性测试。
- 已发送图片是否允许在历史消息中返回小缩略图；若原图不在时，应显示附件缺失状态而非失败整个会话。
