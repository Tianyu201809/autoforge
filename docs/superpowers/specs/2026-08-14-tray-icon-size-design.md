# 托盘图标尺寸修复设计

日期：2026-08-14

## 背景

Windows 托盘中的 Autoforge 图标视觉尺寸明显小于相邻图标。当前 `build/icon-tray.png` 虽然是 32×32 像素，但有效非透明区域只有约 24×25 像素，四周约 4 像素的透明边缘会随系统缩放一起保留。Windows 将图标显示到约 16×16 像素时，有效图形因此只剩约 12×12 像素。

## 目标

- 托盘中的有效图形由约 12×12 像素提升到约 15×15 像素。
- 保留 1 像素透明安全边距，避免不同 DPI 和系统缩放下切边。
- 保持现有蓝色圆形、橙色锻造标识和透明背景不变。
- 让托盘资源可通过现有图标生成脚本重复生成。

## 不在范围内

- 不修改应用主图标、安装包图标或窗口标题栏图标。
- 不修改悬浮球图标。
- 不修改托盘菜单、点击行为或托盘模式设置。
- 不重新设计品牌标识或配色。

## 方案比较

### 方案 A：仅手工替换托盘 PNG

直接裁剪并覆盖 `build/icon-tray.png`，改动最少，但后续重新生成图标时无法稳定复现，容易再次出现透明边缘问题。

### 方案 B：生成器裁边并保留 1px 安全边距（采用）

扩展 `scripts/generate-icons.mjs`，从现有 `logo-mark.png` 读取品牌图标，按 alpha 通道裁掉透明边缘，将内容缩放到 30×30 像素，再居中放入透明的 32×32 画布。生成后的 `build/icon-tray.png` 与脚本一同提交。

该方案有效图形约占画布的 94%，在 Windows 托盘中约为 15×15 像素，同时给抗锯齿边缘留出安全空间。

### 方案 C：运行时裁剪和缩放

在 Electron 启动时使用 `nativeImage` 处理现有图片。它能绕过错误资源，但增加运行时逻辑，且无法从源头保证打包资源正确，不采用。

## 生成流程

`scripts/generate-icons.mjs` 继续生成现有的应用 PNG 和 ICO，并新增托盘 PNG 输出：

1. 读取 `src/renderer/src/assets/logo-mark.png`。
2. 使用 alpha 通道裁掉外部透明像素。
3. 等比缩放到不超过 30×30 像素。
4. 在四周补透明像素并居中到 32×32 画布。
5. 以 PNG 写入 `build/icon-tray.png`。

托盘加载逻辑继续优先读取 `icon-tray.png`，无需改变运行时尺寸判断。

## 验证

- 断言生成文件尺寸为 32×32 像素。
- 断言有效 alpha 边界不超过 30×30，且在画布中居中。
- 运行图标生成脚本，确认应用 PNG、ICO 和托盘 PNG 均成功产出。
- 在 Windows 托盘模式下截图检查，与相邻系统托盘图标比较视觉大小并确认无切边。
- 运行现有单元测试、代码检查和生产构建，确认无回归。

## 完成标准

- 托盘图标有效区域约为 30×30 像素，四周保留 1 像素透明边距。
- 系统托盘中的图标明显大于修复前，且外圈完整、无裁切。
- 图标生成流程可重复得到相同结果。
